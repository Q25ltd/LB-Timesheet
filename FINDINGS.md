# LogisticBay Timesheets — Finding Register

> **This is the canonical registry for every `F-XX` finding ID used anywhere in
> this repository.** Going forward, an F-number is assigned here first; no
> other doc, comment, or test invents one. `STATUS.md` remains the source of
> truth for *current build state*; this file is the source of truth for *what
> each finding ID means and where it stands*.
>
> Built 2026-08-30 by reconstructing every `F-[0-9]{2}` reference from the
> working tree and the full commit history (`git log --all`, 15 commits, all
> on `main`). Two genuine ID collisions turned up during reconstruction
> (`F-03` and `F-04`, both the result of a later commit reusing an ID that was
> already closed) — both are now resolved; see **Collision history** below for
> how and why.

Status vocabulary: `OPEN` · `CLOSED` · `ACCEPTED` · `DEFERRED` · `PARTIAL` ·
`AUTHORIZED` (remediation decided and authorized by the owner, **not yet
proven**). Authorization is not closure: only executable evidence closes a
finding, and F-19's closure below records exactly what its evidence proves and
what it does not.

**`DEFERRED` requires a mandatory trigger** (owner decision, 2026-09-12;
AGENT_WORKFLOW.md §19). Every deferred entry states why it is not being fixed
now, the current risk, and the **lifecycle gate** at which it must be resolved —
`PUBLIC DEPLOYMENT GATE` · `RELEASE / APP STORE GATE` ·
`BEFORE SUBMISSION IMPLEMENTATION` · `BEFORE COMPANY ONBOARDING`. A limitation
that is intentional and will not be fixed is `ACCEPTED` with its reason, not
`DEFERRED`. Deferral without a trigger is a forgotten defect wearing a status.

**Deferred planned features are not findings.** Email verification was unbuilt
planned work governed by D24, not a defect, and deliberately had no F-number;
it is now built (D47, 2026-10-01).
`F-39` is the next free ID.

**Reading historical entries:** descriptions and original probes preserve the
baseline on which a finding was raised. Follow the current Status/Resolution
and STATUS.md for implementation: D63 supersedes old invitation/onboarding gaps,
D66 supplies the submission design, and D57 supersedes the earlier limiter and
production-start conditions. Historical text is not a new open requirement or
authority to reopen a closed finding. No security audit is erased.

## Known sub-issues tracked without their own ID

- **A crafted F-21 cross-column collision denies the rightful credential holder** (independent authentication audit of `049cc37`, 2026-09-12; audit severity Informational). When one Session's current digest equals another's previous digest, `rotateCurrent`'s write into the unique `previousRefreshTokenHash` column raises `P2002`, which `appliedOrNot` collapses to the canonical `401` — so the legitimate holder is refused rotation rather than the wrong Session being rotated. **Fail-closed, and neither Session is mutated**, which the audit confirmed directly. Reaching the state requires a 256-bit CSPRNG collision, so it is not a production path. **Accepted as informational; no ID and no architecture to build for it** — F-21's closure already records that the cross-column state remains permitted by the schema and that the claim is about deterministic resolution, not impossibility.

- **`routePatterns.ts` paren-depth matcher blind spot** (surfaced during F-10's adversarial review): the static `route-declares-auth` check can be defeated by an unbalanced `(` inside a string/template literal in a route handler, causing a false negative. Recorded as a cleanup item in `STATUS.md`'s "Known limitations / cleanup backlog" section, not as a numbered finding.

- **`db-check` can force-drop a fixed database name on whatever server `DATABASE_URL` points at** (backend foundation audit, 2026-08-31; audit severity Low). `api/scripts/db-check.ts:56` issues `DROP DATABASE IF EXISTS "lb_timesheet_check" WITH (FORCE)`; the naming convention is not a structural safety barrier the way `db-smoke`'s explicit `NODE_ENV` + database-name guard is. **Non-blocking backlog** — recorded in `STATUS.md`'s cleanup backlog, not given an ID. - **`AuthStore` over-fetches the Session row** (backend foundation audit, 2026-08-31; audit severity Low). `api/src/lib/authStore.ts:62` selects the whole row — refresh-token hashes included — and narrows it in memory.
